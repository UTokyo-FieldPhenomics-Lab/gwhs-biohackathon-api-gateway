# The DGX's four cards, each its own machine

**2026-11-06, 01:20–02:00 JST.** The first half of the pool re-allocation: every model a V100 can run
is now deployed on the DGX Station, one container per (card, model), and nothing on the 3090, 4090 or
5090 was touched — those machines are in use by others. Constraints are in
[`rules/backend-pool.md`](../rules/backend-pool.md) and [`rules/models.md`](../rules/models.md).

## What was measured, before any deployment

One container at a time on a V100, through its own port with `X-Backend-Token`, one real call:

| id | dtype reported | first answer | worked |
|---|---|---|---|
| `tasselnetv4` | `float32` | count 16.8 on `gwhd` row 0, 0.37 s | yes |
| `gwfss-segformer-b4` | `float32` | head/stem/leaf mask, 0.48 s | yes |
| `dinov3-vitl16` | `float16` (its own capability choice) | **500, `ValueError: Out of range float values are not JSON compliant: nan`** | **no** |
| `dinov3-vitl16` | `float32` (`DINOV3_DTYPE`) | 1024-dim, 32×32 grid, 2.8 MB, 0.49 s | yes |
| `dinov3-vith16plus` | `float32` | 1280-dim, 24×24 grid, 2.0 MB, 0.54 s | yes |
| `sprout-l-gwfss` | `float32` | three class objects, 0.89 s | yes |
| `yolo26-ultralytics` | `float32` | "potted plant" 0.73 on `dev/potted-plant.jpg`, 0.49 s | yes |
| `yolo26-seg-ultralytics` | `float32` | same object with RLE, 0.49 s | yes |
| `wevisone-vl-4b` | `float16` | 43 objects, 23.6 s (its recorded figure is 24.5 s) | yes |

**The DINOv3 containers do not survive fp16 on Volta.** They choose their dtype from the compute
capability — `bfloat16` at 8.0 and above, `float16` below — and on a V100 that cast turns the
answer's feature grid into NaN, which the JSON encoder then refuses, so every call is a `500` with
`Internal Server Error` in the body and the traceback only in the container log. This is the failure
class [`rules/models.md`](../rules/models.md) records from `wevisone-vl-4b`: a cast reaches
non-persistent buffers, and a model that "runs" is not a model that answers. The safe fix is in the
container (default to `float32` below compute capability 8.0, or bound the frequencies as
`wevisone` does); until that is built, both ids are pinned on this host with
`-e DINOV3_DTYPE=float32`, which is the sanctioned use of the override and shows up honestly as
`computed_by.dtype: float32`. **The 3090 and 5090 keep bf16 and are unaffected.**

`sam3.1-meta` and `internvl-u` are absent here by decision, not by measurement: the first demands
bfloat16 hardware, and the second ships bf16 weights with no fp16 conversion ever measured.

## The images

Four of the eight were already on the DGX (`gwfss-segformer-b4`, `tasselnetv4`, `wevisone-vl-4b`).
The other five were built there, not copied: the workstation→DGX path measured **8 MB/s** (500 MB in
65 s, 1 Gb/s NIC, campus path between `192.168.250.0/24` and `192.168.254.0/24`), so the 100 GB of
images would have cost four hours while the builds cost ~25 GB of downloads and 15 minutes. The
build contexts travel as `git archive` tarballs from the submodule (50–74 KB each), and the images
build from the locked environment on the machine that will run them:

    git -C models archive --format=tar.gz --prefix=dinov3/ -o dinov3.tar.gz HEAD:dinov3

`DOCKER_CONFIG=/tmp/dcfg-empty` avoids the registry credential helper for fully public base images.
The ECR repositories (`dinov3-*`, `gwfss-*`, `sam3.1-*`, `tasselnetv4`, `internvl-u`) were the other
option and would have been slower: the compressed layers are still tens of gigabytes over the same
link.

## What runs where

Ports follow `12700 + 10 × card + model slot`, where the slot is the model's own number minus
12710. Card 1 therefore lands on the existing `12711`–`12720` and the single-card machines are
unchanged; a second copy of one model on one host needs a port of its own, because one address
cannot tell two cards apart.

| card | machine | containers (host port) | used of 31 GB |
|---|---|---|---|
| 0 (desktop) | `dgx-v100-0` | gwfss 12702 · tassel 12703 · dinov3-L 12704 · dinov3-H+ 12705 · yolo 12707 · yolo-seg 12708 · sprout 12709 | 12.5 |
| 1 | `dgx-v100-1` | wevisone 12720 · gwfss 12712 · tassel 12713 · dinov3-L 12714 | 20.9 |
| 2 | `dgx-v100-2` | wevisone 12730 · dinov3-H+ 12725 · sprout 12729 | 23.6 |
| 3 | `dgx-v100-3` | wevisone 12740 · tassel 12733 · yolo 12737 · yolo-seg 12738 | 15.3 |

Copies: wevisone 3, tassel 3, gwfss 2, sprout 2, DINOv3-L 2, DINOv3-H+ 2, yolo 2, yolo-seg 2 —
every id a V100 can run has at least two cards. Card 0 carries the desktop and only 40 % of the card,
so a new model has room on the card that cannot host `wevisone` at full batch.

Card 2's hour is the one to watch: `wevisone` holds about 15.2 GB once it has answered, beside
`dinov3-vith16plus` (fp32) and `sprout`. The 23.6 GB above is that peak, measured after the gateway's
own call, not the idle figure.

## The gateway

`~/.config/biohack-gateway/models.json` gained one URL per (card, model) — a backup first, then an
idempotent script that appends to the existing list or `urls` field and preserves mode 0600. The
service restarted and took **about 90 s** to serve again: the initial pool probes the two down
machines serially (the home host refused, the Intel host timed out at connect), and `curl` in that
window returns `000`. That is the documented 503-ish startup, not a failure.

`GET /pool` afterwards reports four machines, each alive, each with exactly its own models. Through
the public API one call per id answered `200`; `tasselnetv4` and `yolo26-ultralytics` were routed to
`dgx-v100-3` and `wevisone-vl-4b` to `dgx-v100-1`. `gwfss`, `sprout` and both DINOv3 ids went to
`lab-3090` because it still scores better — that is routing working, not the DGX failing; the direct
calls above and the `/pool` probes are the proof that those cards answer.

## Lessons

- **Measure the cast, not the start-up.** DINOv3 loaded, answered `/health` and reported its card;
  only a real request revealed NaN. Any card added to this pool needs one real call per model, and
  the dtype in `computed_by` is the first thing to read.
- **A multi-card host needs a port per (card, model) and a machine name per card.** Four containers
  answering `dgx-v100` would have made the gateway sum four queues into one and pass work over while
  three cards idled.
- **The campus link is the constraint, not the disk.** 8 MB/s makes building on the target machine
  the cheap path; the images are reproducible from the submodule plus the locked environment, so
  nothing needs a faster link.
- **A 25 GB build on a serving host is fine.** Builds do not touch the GPU; `wevisone` served through
  the whole session.
