# lab-intel3090 back online, with internvl-u on it

**2026-11-06, 01:40–02:35 JST.** `internvl-u` had no live backend — its only URL was the home 4090,
whose containers were stopped on 2026-11-03 — and `lab-intel3090`, the machine that could take it,
had been unreachable for two days. This is how it was diagnosed, brought back, and given the model.

## The machine was up but not serving

From the DGX, on the same LAN: the machine's address resolved in ARP to a MAC and answered
**3389 (RDP)**,
while 22, 135, 139, 445, 5985, 5986 and `12711`–`12713` all timed out. So it was a Windows box that
was powered on and on the network, with nothing else listening.

The console session confirmed it: Windows Update had left the machine at a post-boot prompt, and
`Get-Service sshd` answered **"Cannot find any service with service name 'sshd'"** — while
`C:\Program Files\OpenSSH\sshd.exe` existed, `Get-WindowsCapability OpenSSH.Server` said `Installed`,
and `ssh-agent` was running. The service registration was gone, not the install.
`winget` reported the package present with no upgrade, so a reinstall would not have repaired it.

```powershell
# from an elevated PowerShell on the machine
New-Service -Name sshd -BinaryPathName '"C:\Program Files\OpenSSH\sshd.exe"' `
  -DisplayName "OpenSSH SSH Server" -StartupType Automatic
Start-Service sshd
```

`administrators_authorized_keys` had survived, so the key worked immediately afterwards.
**A Windows update can take the service and leave the binary**; `Get-Service sshd` is the check, not
the presence of the exe.

## Docker Desktop is per-user, and `start` over SSH does not reach the console

With ssh up, the box still had no engine: `docker version` reported the
`dockerDesktopLinuxEngine` pipe missing, `tasklist` had no `Docker Desktop.exe`, and both WSL
distros were `Stopped`. The install is **per-user**, at
`%LOCALAPPDATA%\Programs\DockerDesktop\Docker Desktop.exe` — `C:\Program Files\Docker` is empty — so
it only runs inside a desktop session, and an SSH session is not one: launching the exe over SSH
printed "launched" and produced no process.

A scheduled task launched **in the console session** does work:

```cmd
schtasks /create /tn gwhs-start-docker /tr "\"%LOCALAPPDATA%\Programs\DockerDesktop\Docker Desktop.exe\"" ^
  /sc once /st 23:59 /it /f
schtasks /run /tn gwhs-start-docker
```

`Docker Desktop.exe` and `com.docker.backend.exe` then appeared under the `Console` session, the
engine came up in about a minute, and the three containers returned by themselves because their run
lines carry `--restart unless-stopped`. The task stays on the machine as the way to start the engine
with nobody at the desk — it still needs `crest` signed in, so it does not replace auto-logon.

## Getting the image there

The image built on the DGX in seconds (the weights layer is cached), but the two boxes are 8 MB/s
apart from the workstation and **118 MB/s** apart from each other — measured with a 500 MB HTTP
transfer, which is the number that decided the route:

- `docker save | gzip -1` was the wrong shape: it wrote 1.4 GB in five minutes and was killed.
- `docker save -o /ssdraid0/tmp/internvl-20261106.tar` wrote **18.4 GB** in about ten minutes and
  renamed the file only when done, so a poll sees nothing until it finishes.
- Serving that file with `python3 -m http.server` and pulling it from the Windows side with `curl`
  took **2.6 minutes** at 118 MB/s.
- `docker load -i` through the Windows named pipe answered `502 Bad Gateway` once; a retry loaded
  the image silently (no "Loaded image" line, but `docker images` had it).

## The response budget had to be fixed first

`internvl-u` declared no `response_timeout_seconds`, so the gateway gave it its ten-second default —
and a picture takes about 11 s even on a 4090. The container now declares **120 s** in `/health`,
which is what the gateway reads; the cap is 180. Deployment without that change would have failed
every picture call and counted the machine as broken.

Measured through the public API afterwards:

| call | result |
|---|---|
| `mode=text`, "Describe this image." | 200 in 10.8 s, prose answer |
| `mode=image`, "Make the background a clear blue sky." | 200 in 49.5 s, `image/png` 1024×1024, 1.57 MB |

`/pool` now lists `lab-intel3090` by alias with `gwfss-segformer-b4`, `internvl-u` and
`tasselnetv4`.

## Left behind

- `C:\Users\CREST\internvl.tar` (18.4 GB) could not be deleted — a handle still holds it, most
  likely Defender scanning a file this size. Delete it when it unlocks.
- The scheduled task `gwhs-start-docker` remains on purpose, documented above.
- The DGX's temporary copy and both HTTP servers were removed.

## Lessons

- **A backend that goes quiet can be a Windows service that a feature update removed.** Ask the
  machine (`Get-Service`), not the install directory.
- **A per-user Docker Desktop needs an interactive session; SSH is not one.** A scheduled task with
  `/it` is the bridge, and only while that user is signed in.
- **Route a large image over the link that is fast.** The same 18 GB is 40 minutes from the
  workstation and 2.6 minutes between the two backends in the same room.
- **`docker load` gives no output when it succeeds** to a pipe this deep: check `docker images`, not
  the log.
