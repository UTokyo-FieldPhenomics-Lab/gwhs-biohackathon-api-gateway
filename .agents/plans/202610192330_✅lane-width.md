## Result of the measurement (2026-10-19)

The card is idle most of the time while requests queue: mean utilisation 18–39 % in row mode and
9–15 % in upload mode, with gaps of 2–6 s, while 95 % of requests were dispatched onto a machine
already carrying work. One request costs 38–86 ms of card time against 687 ms end to end, so the pool
is network-bound rather than GPU-bound. For uploads a wider declaration buys nothing until
`predict_upload` stops blocking the event loop. Details and data:
[`2026101923_gpu-occupancy.md`](../references/2026101923_gpu-occupancy.md).

## What we got wrong in the last round

Both containers hold a **global `threading.Lock` around the GPU work**
(`models/sam31_official/serve.py:892`, `models/gwfss_segformer/serve.py:579`), and the sam31
README says why: the processor keeps the current image on itself, so concurrent inference is not
correct, not merely slow. **The card already runs one inference at a time, by design.**

So the flat gateway-side latency at `ahead=5` was not the card interleaving four requests. It was
the image fetch and the HTTP transfer overlapping with the lock, which is I/O, not compute. The
"four wide" reading in
[`202610192300_lane-width-and-the-score.md`](../references/202610192300_lane-width-and-the-score.md)
overstates it and must be corrected by the measurement below.

And `max_in_flight` is not enforced anywhere on dispatch: it is summed into the per-token cap and
published in `GET /models`. Nothing about it idles a GPU.

## Task 1 — decouple the cap, first

The cap today is `pool_width()` = sum of declared widths = 3. Raising a declaration to 4 would make
it 12 silently. So this lands before any declaration changes.

- `app.py:451`: provider is a policy constant (3), still overridable by
  `BIOHACK_MAX_CONCURRENT_PER_TOKEN`, no longer derived from the pool.
- `limits.py`: rewrite the rationale. Capacity is a measured hardware fact; the cap is a fairness
  policy. They must be free to disagree, and today's argument for coupling them is the thing to
  retire.
- `models.py`: `pool_width()` has no remaining caller — remove it. `ModelSummary.max_in_flight`
  already computes its own sum and stays as the published capacity.
- Tests: `test_a_token_cannot_hold_more_than_three_requests_at_once` asserts the coupling; rewrite
  it to assert the opposite, including the case where the pool declares four per backend.

Acceptance: with declarations at 1 or at 4, one key may hold 3.

## Task 2 — occupancy, not a width sweep

A width sweep would have measured queueing, not parallelism, because the lock serialises the work.
What we need to know is whether the card is **ever idle while requests are waiting**.

Both containers already publish the signal: `/health` returns
`"in_flight": 1 if LOCK.locked() else 0`, plus `gpu_free_mib`.

- Client: a machine that is not the target (last time the generator ran on a backend). Sweep each
  machine from another one.
- Load: the 8001 instance with the cap off, 50 simultaneous, held for 60 s rather than a burst.
- Poll each container's `/health` at 5 Hz for the whole run; record the fraction of samples with
  `in_flight = 1`, and sample `nvidia-smi` (utilization, memory, power) on each machine.
- Run row mode and upload mode separately: an upload's body crosses the network while the lock is
  free, so the two modes can have very different occupancy.
- Repeat per machine; the 24 GB cards and the 32 GB card may differ.

Deliverable: occupancy per machine per mode, plus whether p95 grows with the queue.

## Task 3 — choose the number

- Occupancy near 1 while requests are queued: the card has no gaps. Keep the declaration at 1,
  correct the reference, and say plainly that there was nothing to lift.
- Occupancy low (0.4–0.7): the container refuses work it could overlap. Raise that machine's
  admission width to the smallest value that keeps occupancy above ~90% without growing p95.

## Task 4 — write it into the declarations

The number lives in the containers, not here: `GWFSS_MAX_IN_FLIGHT` for segformer (default 1),
`SAM31_*` for sam31, in the private `models/` submodule and each machine's run line. After a restart,
`GET /models` must publish the new sum, and the cap must stay 3 (Task 1).

Also fix `models/sam31_official/README.md`: its "`max_in_flight` is 1" paragraph is right about the
card and wrong about admission, and the text should separate the two.

## Task 5 — recalibrate and record

`DELAY_PER_QUEUED_REQUEST` (0.25 row / 0.5 upload) assumes four requests answer at once. If
occupancy shows the card serialises, the marginal cost of one queued request is the *fetch overlap*,
not a quarter of a service time, and the constant should be the measured marginal — possibly near
zero, which would make the router prefer the nearest machine almost regardless of queue. Record the
result in a new reference and amend the 2026-10-19 one where it says "four wide".

## Risks

- The generator must not run on a backend; a third of the last run's requests shared a machine.
- The 5090 is a Windows workstation someone uses; schedule the 60 s bursts accordingly.
- Use the 8001 instance, not production: 50 simultaneous on the live surface is a participant's view.
- A 24 GB card carries ~8.5 GB resident; admission width must leave room, and `gpu_free_mib` is the
  check.
