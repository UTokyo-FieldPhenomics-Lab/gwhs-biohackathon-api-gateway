# The model page: an example you can read, and a page you can run

Status: **planned, nothing implemented** (2026-10-16). The design below was settled with the user.
Two deliverables, in this order: the documentation site's model page, then the framed `/play` page on
the gateway. **The recorded example is deliberately last** — the user is tuning the prompt and
threshold against the published datasets and will supply the parameters and the result, so nothing
here may invent one.

Owner files (proposed): `docs/content/models/index.md` (new), `docs/content/models/demo.js` (new),
`gateway/src/biohack_gateway/play.py` (new), `gateway/src/biohack_gateway/app.py`,
`docs/content/api/frame.js`, `zensical.toml`.

## Goal and acceptance

A reader on the documentation site sees a real mask decoded in the browser, and a reader with a key
runs one inference from that same page and sees the mask it returns — without the site ever holding
a key, and without the gateway gaining a second copy of the geometry contract.

Acceptance:

- **A reader with no key sees a real decoded mask.** The page is not empty before anyone types
  anything.
- **A reader with a key gets a live result on the page**, for a published row or for their own
  photograph.
- **Supporting a new model requires no change to the page.** This is the invariant worth holding the
  work to: the page is built from `GET /models` and `GET /datasets` alone, so a model that the page
  cannot render is a declaration that is incomplete — not a page that is not clever enough. The page
  is the declaration mechanism's first consumer, and the only one that would expose a missing field
  immediately.
- **The key never leaves the framed page**, and is not stored anywhere.

## What already exists, so nobody rebuilds it

- **The framed-page mechanism.** `docs/content/interactive.md` is an `<iframe>` to
  `https://api.global-wheat.com/docs`, `docs/content/api/frame.js` sizes it cross-origin over
  `postMessage` and passes the reader's palette into it, and the gateway permits exactly that one
  origin through `DOCS_PARENT_ORIGIN` and a `frame-ancestors` CSP. `/play` reuses all of it: the
  reporter it needs is `SWAGGER_FRAME_REPORTER`, which should be extracted so both pages share one
  copy rather than two, and `frame.js`'s selector, hard-coded to `#reference-frame iframe`, should
  become semantic so one file can size two frames.
- **The normative decoder, as a downloadable file.** `docs/content/post-processing/rle_decode.js` is
  26 lines and sets a **global** `rleDecode` (no module export), and the site serves it as
  `application/javascript`. So a page can load the very file the documentation tells participants to
  download — the demo then cannot drift from the tutorial, because it is the tutorial's file. Load
  it by URL rather than copying it, and say so plainly on the page if it fails to load instead of
  rendering an empty canvas.
- **The model surface.** `GET /models` answers each model's id, `resolution`, `backends_up`,
  `max_in_flight` and its `parameters` with defaults and bounds;
  `POST /models/{model}/predict` takes `{"dataset": str, "row": int}` plus the parameters as query
  parameters; `POST /models/{model}/predict/upload` takes the image bytes as the body. Everything
  behind it is in [`2026101617_model-api-surface.md`](2026101617_model-api-surface.md).
- **`data.global-wheat.com` needs no key**, and its objects are `immutable` with a one-year TTL.
- **A precedent for serving a page from the gateway**: `/docs` and its stylesheets
  (`swagger_dark.css`, `swagger_trim.css`) live beside `app.py` and are inlined at import. `/play`
  should follow the same shape — one module, one stylesheet beside it, no static mount.

## Layer 1 — the documentation page

A new `Models` page, in the nav after `Datasets`: the model ids and what each one is, the parameters
it accepts with their defaults, how to call it (`curl` and `fetch`, including the upload route), and
the browser demo.

- **The map of models is written by hand and says so.** The build has no API key and must not need
  one, so the page cannot fetch `GET /models` at build time; it shows what that call answers today
  and gives the `curl` that shows it live.
- **The demo panel** is a `<canvas>` that loads a published image from `data.`, a **recorded
  response** committed beside the page, and the decoder file above; it draws the image, each
  object's mask, and its `bbox`, and it keeps the check the site already makes in prose — the
  decoded pixel count equals `area` — as a live line. **This is the part waiting on the user's tuned
  parameters.**
- **Do not restate the post-processing page.** The decode itself, the three languages, and the
  `area` check are already there; the model page links to it rather than explaining it again.
- The page must be honest about what the model does, with the measured numbers from
  [`2026101617_model-api-surface.md`](2026101617_model-api-surface.md#measured-facts): a conspicuous
  head in a close-up is segmented, the small dense heads of a field crop are not, and the mask's
  boundary is coarse at full resolution because the mask is computed at the container's resolution.

## Layer 2 — `/play` on the gateway

A page served by the gateway itself, framed from the `Models` page exactly as the reference is from
`interactive.md`. Serving it from the API host is what makes the live call possible at all: the page
is **same-origin with the API, so no CORS is involved anywhere**, and the reader's key is typed into
the page that uses it.

- `/play` joins `OPEN_PATHS`, answers `include_in_schema=False`, and carries
  `frame-ancestors {DOCS_PARENT_ORIGIN}` — the same treatment as `/docs`, and it earns it the same
  way: it carries no data, and it is where a reader puts their key.
- **The page is five rows and nothing more**: a model selector (filled from `GET /models`, showing
  `backends_up`) and the key field; the image choice, either `dataset` + `row` or an upload;
  the model's own parameters; one button; and the canvas with the live `Σ mask = area` line and the
  response body in a `<details>`.
- **The controls are generated from the selected model's declaration**, never hard-coded, and the
  region is rebuilt when the model changes with each field prefilled from its declared default. The
  inference rule for a field, which is the whole of it:

  | Declared as | Control |
  |---|---|
  | a number with both `minimum` and `maximum` | a slider |
  | a number with either bound missing | a number input |
  | `true` or `false` | a checkbox |
  | anything else | a text input |

  Inference cannot be silently wrong, which is why it is enough: an unmapped parameter degrades to a
  text input, the backend is the validator, and its `400` is printed on the page verbatim. Its
  ceiling is an enumerated parameter — a prompt that must be one of three class names — and that is
  the trigger for adding an explicit `type` (and `values`) to `ModelParameter` in the gateway and to
  the container's declaration. Not before: no model needs it yet.
- **A model with no parameters has no controls** and needs no special case, and a model whose
  backends have not declared themselves shows no controls plus a line saying so and `backends_up: 0`
  — so the page explains why nothing can be run instead of letting a reader press a button and wait
  for a timeout.
- **Deliberately not in `/play`**: a dataset browser (no row listing, no paging — `/datasets` and
  the reference already do that), a per-object list, per-object highlighting, the raw `counts`
  string, history, downloads, and any frontend framework or build step. One HTML-shaped page and the
  stylesheet beside it.
- **The upload sends the file as the body**: `fetch(url, { method: "POST", body: file })`, because
  the container takes raw bytes — the design that made the backend's route simple makes the page's
  simplest branch work too.
- The key is held in a variable for the page's lifetime and written nowhere.

## Facts from the browser that shape the code

- **`data.global-wheat.com` sends no `access-control-allow-origin` header.** So an `<img>` must
  **not** carry `crossorigin` (the image would fail to load), the canvas is tainted, and **no pixel
  may be read back**. Drawing a mask over the image therefore goes through an offscreen canvas:
  `putImageData` the mask there, then `drawImage` that onto the visible canvas, which composites
  without any read. The `Σ mask = area` check reads the decoded array, never the canvas, so the
  constraint costs nothing.
- `rle_decode.js` sets a global, so a plain `<script src>` loads it; nothing needs a module loader.
- The reference page floats on `swagger-ui-dist@5`, which is why its selectors were taken from the
  bundle rather than guessed. `/play` has no such problem — it renders its own markup.
